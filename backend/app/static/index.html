Acquisition Notes

Raw GNSS, IMU, battery and vehicle-status messages are stored separately. GNSS or odometry updates trigger the baseline normalizer, which emits unified telemetry.

Vehicle status uses heartbeat or telemetry while a mission is RUNNING. A completed or aborted mission becomes INACTIVE, not OFFLINE. Sensor status is calculated separately from each sensor's own data stream.

Running thresholds: ONLINE ≤ 5 seconds, DEGRADED ≤ 15 seconds, otherwise OFFLINE.

v0.4.1 integrity engine: sequence, sampling-rate, communication-latency and timestamp faults are persisted as Integrity Events. Recoverable rate and latency alerts are automatically resolved after a healthy evaluation window; historical faults remain available for review.

v0.4.2 operational health: backend uptime, database health, HTTP/MQTT rates, WebSocket clients, process resources, structured application logs and platform alerts are monitored independently from vehicle data alerts.

v0.4.3 storage lifecycle: pagination, retention preview, manual cleanup, background export jobs, backups and SQLite maintenance are available. Destructive operations require explicit confirmation.

v0.5.0 vehicle profiles: select UGV, UAV, AUV or USV profiles in the console or pass the same profile through CLI parameters. Every Mission stores the resolved profile, capabilities, parameters, scenario and random seed.

v0.5.1 environment context: scenario templates contain obstacles, vehicle-specific constraints and external fields. Simulation startup filters them by vehicle type and capabilities, then stores an immutable Mission environment snapshot.

v0.5.2 obstacle interaction: vehicle-specific safety envelopes, nearest-obstacle clearance, time-to-collision estimates and basic obstacle-aware trajectory generation are available. These are research and simulation features, not certified control functions.
