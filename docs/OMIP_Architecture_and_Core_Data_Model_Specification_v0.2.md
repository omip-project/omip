# OMIP Architecture and Core Data Model Specification v0.2

## 1. Purpose

OMIP v0.2 is a simulation-first platform for collecting, organising, reviewing and exporting autonomous or connected vehicle telemetry. Its purpose is to establish a stable data pipeline before physical hardware, advanced vehicle simulators or research algorithms are introduced.

The main design change from v0.1 is that telemetry is no longer treated only as a stream from a vehicle. Every telemetry frame is organised within a mission. This allows the platform to preserve experimental context, replay a run and produce a dataset suitable for later analysis.

## 2. Scope

OMIP v0.2 provides:

- mission lifecycle management;
- telemetry ingestion and validation;
- SQLite persistence;
- live WebSocket distribution;
- configurable trajectory scenarios;
- historical replay;
- CSV and JSONL export; and
- mission-level data-quality summaries.

The following remain outside the v0.2 scope:

- vehicle control commands;
- safety-critical operation;
- real-time path planning;
- camera, LiDAR and point-cloud storage;
- user authentication;
- cloud deployment; and
- distributed message brokers.

## 4. Core entities

### 4.1 Mission

A mission represents one bounded data-collection or simulation run.

| Field | Description |
|---|---|
| `mission_id` | Stable identifier supplied by the simulator or generated by the platform |
| `vehicle_id` | Vehicle associated with the mission |
| `name` | Human-readable mission name |
| `scenario_name` | Scenario configuration used for the mission |
| `status` | `PLANNED`, `RUNNING`, `COMPLETED` or `ABORTED` |
| `description` | Free-text purpose or experiment description |
| `metadata` | Additional structured experiment information |
| `created_at_utc` | Mission registration time |
| `started_at_utc` | Mission start time |
| `ended_at_utc` | Completion or abort time |

Valid lifecycle transitions are:

```text
PLANNED -> RUNNING -> COMPLETED
    |          |
    +----------+----> ABORTED
```

Completed and aborted missions are terminal in v0.2.

### 4.2 Telemetry frame

A telemetry frame is an immutable time-stamped observation associated with one vehicle and one mission.

Top-level identity fields:

- `schema_version`
- `message_id`
- `vehicle_id`
- `mission_id`
- `sequence_no`
- `timestamp_utc`
- `source`
- `coordinate_frame`

Nested data groups:

- `position`
- `velocity`
- `acceleration`
- `orientation`
- `state`
- `quality`

Server-generated fields:

- `received_at_utc`
- `latency_ms`

### 4.3 Scenario

A scenario is a JSON file consumed by the simulator. It contains controlled parameters used to generate repeatable data.

The v0.2 scenario model includes:

- forward velocity;
- lateral wave terms;
- vertical wave terms;
- battery model;
- mode schedule;
- random seed;
- position noise;
- confidence;
- periodic invalid frames; and
- periodic dropped frames.

A wave term is represented by amplitude, time scale and phase:

```text
position(t) = amplitude × sin(t / time_scale + phase)
```

Velocity and acceleration are calculated analytically from the same term, ensuring internal consistency between position, velocity and acceleration.

## 5. Storage model

### 5.1 `missions` table

The mission table stores one row per mission. Mission metadata is stored as JSON to permit additional experiment-specific fields without an immediate schema migration.

### 5.2 `telemetry` table

The telemetry table stores:

- searchable scalar fields such as mission, vehicle, time, sequence, speed and quality;
- server-computed latency; and
- the complete validated payload as JSON.

This hybrid model supports efficient common queries while retaining the complete source record.

Indexes support:

- latest telemetry by vehicle;
- ordered telemetry by mission; and
- sequence analysis by mission.

## 6. Data-quality calculations

OMIP v0.2 calculates mission-level indicators from stored telemetry.

### 6.1 Missing frames

Missing frames are inferred from gaps in the sequence number. For example:

```text
0, 1, 2, 5, 6
```

indicates two missing frames: sequence numbers 3 and 4.

### 6.2 Invalid frames

The invalid-frame count is the number of records for which:

```text
quality.valid = false
```

Invalid frames are retained because their presence may be important to later analysis.

### 6.3 Telemetry rate

For a mission containing more than one frame:

```text
average_rate_hz = (frame_count - 1) / mission_data_duration_seconds
```

### 6.4 Ingestion latency

For each frame:

```text
latency_ms = received_at_utc - timestamp_utc
```

OMIP stores the value and reports mission average and maximum latency.

## 7. Replay design

Replay is client-driven in v0.2:

1. The browser requests ordered mission telemetry.
2. The browser stores the returned frames in memory.
3. A timeline selects the current record.
4. Play mode advances according to telemetry timestamps.
5. Speed selection scales the interval between records.

This is suitable for small experimental datasets. Server-side streamed replay should be considered when mission datasets become large.

## 8. Export design

JSONL preserves the complete nested telemetry payload, one record per line.

CSV flattens the nested fields into columns so that the dataset can be loaded directly into spreadsheet, statistical and machine-learning tools.

Exports are generated per mission to preserve experiment boundaries.

## 9. Reliability and limitations

The current implementation is a development platform, not a safety-critical system.

Important limitations include:

- SQLite is intended for one local development instance;
- WebSocket connections are stored in application memory;
- there is no authentication or authorisation;
- export generation loads the mission dataset into memory;
- CORS is unrestricted for local development; and
- HTTP ingestion does not provide broker-level delivery guarantees.

## 10. Direction for v0.3

The next architecture milestone should add a general acquisition layer:

- HTTP and MQTT adapters;
- vehicle and sensor registry;
- topic-based raw observations;
- event and annotation records;
- batch ingestion;
- experiment configuration snapshots;
- PostgreSQL or TimescaleDB; and
- containerised local deployment.
